# 07. План создания продукта

**Версия 1 от 19.10.2026.** План живой: лид обновляет его после каждой контрольной точки и при изменении обстоятельств (ответы экспертов, сроки, доступы). Неизменно одно: продукт должен быть создан и должен быть безупречным. Поэтому план устроен так, что на любом этапе у нас есть работающая, честная версия, а каждая следующая только добавляет ценность.

**Принципы:**
1. **Ценность для пользователя важнее числа функций.** Каждая функция отвечает на вопрос «что сотрудник агентства сделает быстрее или увереннее».
2. **Два ключевых шага (требование команды):**
   - а) UX-мокап с точным визуалом и имитацией работы. Смотрим и правим, пока он не станет безупречным;
   - б) реализация бизнес-приложения строго по мокапу, с безупречными бэкендом и фронтендом.
3. **Никаких выдуманных данных в продукте.** Ссылки, даты, тексты берутся только из реальных постов (красная линия 1, К14). Демо-данные бывают только в мокапе, и он так и помечен.
4. **Мокап и продукт — один код интерфейса.** Мокап пишем на той же технологии, что и продукт, с имитацией сервера. При реализации имитацию заменяем настоящим сервером, и визуал не «расползается».
5. **Лид бережёт контекст.** Объёмная работа уходит исполнителям по брифам, результаты лежат в `docs/`, лид принимает их и сдаёт команде.

## Технологии (выбор лида; уточняется на этапе технического проекта)

| Слой | Выбор | Почему |
|---|---|---|
| Интерфейс (мокап и продукт) | React + TypeScript (strict) + Vite; доступные примитивы Radix UI; стили на дизайн-токенах из референсов команды | Один код для сайта и расширения; Radix даёт клавиатуру и скринридер из коробки (сценарии доступности) |
| Имитация сервера в мокапе | Слой API-клиента с фиктивной реализацией по тому же контракту, что у настоящего API | При реализации меняем только реализацию клиента, экраны не трогаем |
| Показ мокапа команде | Сборка в одну HTML-страницу, публикация ссылкой (Artifact) плюс локальный запуск | Команда открывает ссылку и кликает, ничего не устанавливая |
| Расширение | Manifest V3, боковая панель с тем же интерфейсом; сборка через WXT (Vite) | ТЗ-Н2; установка через ZIP и режим разработчика (`research/extension-feasibility.md`) |
| Сервер | Python 3.12 + FastAPI + Pydantic v2 | Лучшая экосистема для обработки русского текста |
| Хранилище | PostgreSQL 16 + pgvector | Одна база для источников, поисков, публикаций и векторов (Р8) |
| Фоновые поиски | Очередь задач, ход поиска передаётся в интерфейс потоком (SSE) | Индикация хода, частичные сбои и повтор (Сц. 5) |
| Отбор (Р5) | datasketch (MinHash), эмбеддинги BERTA или USER2-base (sentence-transformers), Natasha (кто, где, когда) | Решение Р5, всё локально |
| Нейросеть (Р6) | GigaChat 3.1 Lightning в Ollama, ответы по JSON-схеме; провайдер задаётся настройкой | Решение Р6, без Яндекса |
| Выгрузка | XLSX на сервере (openpyxl) из тех же данных, что на экране | «Файл совпадает с экраном» (ТЗ-Ф38) |
| Сбор данных | Отдельный адаптер на каждую площадку с общим интерфейсом и проверкой каждой ссылки живым запросом | Р2; площадки меняются независимо |
| Развёртывание | Docker Compose, HTTPS через Caddy, сервер организаторов или VPS в РФ | Стенд для экспертов (М-Н6) |
| Качество | ruff, mypy, pytest; ESLint, tsc; Playwright e2e по must-сценариям; оценка качества отбора на мини-эталоне; CI на каждый коммит | «Безупречно» проверяется автоматически, а не на глаз |

### Этап 1. UX-мокап (шаг «а»)

1. **Информационная архитектура и пользовательские пути.** Экраны и переходы из must-сценариев `05-scenarios.md`: запрос → условия → ход поиска → подборка → карточка → группа → «Распространение» → выгрузка; пустой результат, частичный сбой, ошибка, повтор; управление источниками; первый запуск. Команда согласует схему до отрисовки.
2. **Визуальный язык по референсам команды и `08-visual-concept.md` (точки):** дизайн-токены (цвета, шрифты, отступы, радиусы), светлая и тёмная тема, сетка для сайта и для боковой панели расширения (≈ 360–400 px).
3. **Кликабельный мокап** с имитацией: реалистичные демо-данные края (помечены как демо), все состояния, задержки и ошибки по сценариям.
4. **Цикл «смотрим — правим».** Команда открывает ссылку, оставляет замечания, лид собирает их в список, исполнитель правит, лид принимает. Повторяем, пока чек-лист не пройдён полностью.

**Чек-лист «мокап безупречен» (КТ1):**
- [ ] каждый must-сценарий проходится мышкой от начала до конца;
- [ ] у каждого экрана есть все состояния: загрузка, пусто, частичный сбой, ошибка, успех;
- [ ] удобно и на 5, и на 500 записях (К26);
- [ ] всё работает с клавиатуры, видимый фокус, контраст по WCAG AA, подписи для скринридера, увеличение до 200% без поломок;
- [ ] тексты понятны человеку без техподготовки, без жаргона (ТЗ-Н4, Н5);
- [ ] видны условия поиска, статус по площадкам, причина региона, метод отбора (Р4, Р9);
- [ ] сайт и боковая панель расширения выглядят как один продукт;
- [ ] визуал совпадает с референсами, единообразие по всем экранам;
- [ ] команда сказала «безупречно».

### Этап 2. Технический проект

- Архитектура: адаптеры площадок → нормализация → воронка отбора → хранилище → API → интерфейс.
- Модель данных: поиск ↔ источник ↔ публикация ↔ размещение ↔ группа (К8); ключ повторов (ТЗ-Ф30); изоляция поисков (ТЗ-Ф45).
- **Контракт API = контракт фиктивного клиента из мокапа.** Расхождений быть не должно.
- План тестов: e2e по must-сценариям, мини-эталон, нагрузочный прогон на 500+ результатов, проверки безопасности (prompt injection в тексте поста, XSS в тексте поста, ограничение частоты запросов).

**КТ2:** команда согласовала архитектуру и контракт.

## Что делать, если обстоятельства меняются

| Если… | То… |
|---|---|
| Сроки короче, чем думали | Срезаем снизу: сначала этап 3.5, потом часть 3.4. Мокап всех сценариев остаётся (страховка К21–К25). Этапы 3.1–3.3 не трогаем |
| MAX или OK недоступны законно | Площадка работает по списку источников с проверкой ссылок, ограничение честно показано в строке состояния и README |
| VK `newsfeed.search` закрыт | Режим «без ограничения» — по широкому пулу сообществ края (Р3) |
| Локальная нейросеть медленная или слабая | Сужаем серую зону, показываем результаты сразу и дополняем метками по мере проверки; запасной вариант — GigaChat API или сервер с GPU |
| Заказчик настаивает на Яндексе | Решение команды; провайдер нейросети меняется настройкой |
| Команда приносит новые фичи | Лид оценивает ценность, стоимость и баллы, команда решает, фича попадает в Р10 и в этап 3.4 или 3.5 |
| Референсы задерживаются | Делаем архитектуру экранов и пути (этап 1, шаг 1), визуал накладываем, когда референсы придут |
