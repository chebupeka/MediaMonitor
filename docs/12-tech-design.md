# 12. Технический проект сервера

**Версия 1 от 19.10.2026.** Шаг «б» плана (`07-plan.md`, этап 2). Код — `server/`, запуск и проверки — `server/README.md`. Контракт — `web/src/api/types.ts` и `client.ts`: сервер отвечает ровно в этой форме, расхождений нет (проверяет тест по JSON Schema из types.ts).

## 1. Модули

```
площадки ─▶ адаптеры ─▶ нормализация ─▶ воронка отбора ─▶ хранилище ─▶ API (JSON + SSE) ─▶ интерфейс
 VK OK MAX   adapters/   normalize/        matcher/          db/          api/               web/ (сайт,
             base.py     ключ, текст,      Matcher +          PostgreSQL   routes.py          расширение)
             fixture.py  край, запрос      заглушка           16+pgvector
             live.py                       ai/ — нейросеть
                         services/ — ход поиска (runner), подборка, выгрузка, распространение, источники, стенд
```

| Модуль | Что делает | Файл |
|---|---|---|
| Адаптер площадки | Даёт кандидатов поиска порциями, пост по ключу, проверку ссылки на группу, здоровье. Сбой — `AdapterError` с кодом контракта; непонятный ответ — `bad-response`, а не «0» (НТ-5) | `adapters/base.py` |
| FixtureAdapter | Записанные примеры из демо-наборов мокапа (`fixtures/*.json`) и сбои: недоступна, непонятный ответ, частота, задержка, таймаут, квота, ключ | `adapters/fixture.py` |
| VK, OK, MAX | Заготовки: интерфейс, ключи из окружения, честное «нет доступа», TODO со ссылками на разведку | `adapters/live.py` |
| Нормализация | Ключ поста и ссылки (НТ-13), предложения, выдержка, места края (Р4), разбор запроса как в мокапе (НТ-21) | `normalize/` |
| Воронка | Интерфейс `Matcher`; воронка «Э-Отбор» (`mm_matching`) через адаптер `funnel.py`; простая заглушка `simple.py` — для тестов | `matcher/` |
| Модель смысла | BERTA на CPU сервера или сервис gpu-node (`EMBEDDINGS_URL`) с откатом на CPU; кэш векторов в памяти и в базе | `matcher/embeddings.py`, `services/vectors.py` |
| Нейросеть | Ollama по `OLLAMA_URL` (родной API или OpenAI-совместимый), ответы по JSON-схеме; спорные посты проверяет нейросеть воронки, сервер — статус, прогрев, карточка темы для заглушки | `ai/judge.py` |
| Ход поиска | Фоновые задачи, очередь, события в базе, остановка, повтор площадки, восстановление после перезапуска | `services/runner.py` |
| Подборка, выгрузка | Одни функции собирают ответ, события, XLSX и «Распространение» — числа совпадают | `services/selection.py`, `export.py`, `spread.py` |
| Проверка текста на ИИ | Одна нормализация, общий кэш `ai_checks`, провайдеры `fixture` / `gigacheck`, фоновая проверка постов подборки (§13) | `aicheck/` |

Поток данных одного поиска: адаптер отдаёт порцию → нормализация → публикации пишутся в общий кэш → привязка к краю по Р4 (режим «Мои источники» — регион не проверяется, человек сам выбрал источники; режим «Везде» — краевой источник или место края в тексте, иначе пост не идёт дальше) → воронка решает по каждому кандидату → записи подборки и группы пишутся в базу → событие `items` в журнал → читатели потока получают его. Сбор и отбор идут параллельно: площадки кладут порции в очередь поиска, один обработчик отбирает их шагами по `MATCH_BATCH_SIZE` (16) постов — первые записи приходят через доли секунды, а не в конце (НТ-2).

## 2. Модель данных

| Сущность | Таблица | Главное |
|---|---|---|
| Рабочее место (Р8) | `workspaces` | `id`, SHA-256 ключа (самого ключа в базе нет), время входа, последний выбранный режим поиска |
| Источник (справочник) | `platform_sources` | id `vk:-100101` / `ok:5600101` / `max:имя`; название, тип, район, подписчики; отметки «краевой» и «в каталоге»; закрыт ли |
| Источник пользователя | `workspace_sources` | своё название, тип, район; откуда добавлен; последняя проверка; мягкое удаление `removed_at` — можно вернуть час (НТ-7) |
| Поиск | `searches` | запрос как есть, условия выполненного поиска (НТ-1), вид, карточка темы, релиз и его абзацы, фаза, пометки, номер последнего события, итог для «Недавних» |
| Ход по площадке | `platform_runs` | состояние из полного набора (НТ-3), счётчик «18 из 40», проблема, потолок выдачи, номер попытки |
| Публикация | `publications` | общий кэш постов (Р7): ключ, ссылка, склеенные адреса, текст, предложения, время и его надёжность, правка, репост, медиа, просмотры, реакции, хеш текста, проверка ссылки |
| Вектор смысла | `post_embeddings` | кэш (Р7): пост × модель с версией (`sergeyzh/BERTA#1`) × задача (`topic` / `paraphrase`), хеш текста, вектор pgvector. Пост, встречавшийся раньше, не считается второй раз, пока текст тот же |
| Проверка на ИИ | `ai_checks` | кэш (§13): `text_hash` (SHA-256 нормализованного текста) × `model` × `model_version` → `score`, `level`, `checked_at`. Первый результат сохраняется и переиспользуется в отдельной проверке, подборке и «Распространении»; «мало текста» и «недоступно» не пишутся |
| Размещение (запись подборки) | `search_items` | публикация в конкретном поиске: метка, метод, причина региона, выдержка (границы), доказательство, тип размещения, цитирование, группа, кластер, «новое», порядок прихода |
| Исключение (ТЗ-Ф48) | `search_items.excluded`, `excluded_at` | отметка на размещении; исключённые не идут в счётчики и XLSX |
| Группа (Р9) | `search_groups` | релиз или копии; ключ кластера от воронки; первоисточник считается по времени |
| События хода | `search_events` | журнал: номер, тип, событие в форме контракта — из него читается SSE |
| Выгрузка | `exports` | журнал выгрузок: поиск, правила, число строк, имя файла (сам файл собирается по запросу из тех же данных) |
| Импорт | `import_previews` | разбор файла (час жизни): `importSources` добавляет ровно строки «добавим» |
| Стенд | `stand_events`, `quota_usage` | события для дежурного; расход квот по периодам и предупреждение 80% |

Миграции — Alembic (`server/migrations`): `0001` — схема и расширение `vector`, `0002` — последний режим рабочего места, `0003` — кэш векторов `post_embeddings`, `0004` — кэш проверки на ИИ `ai_checks`. Время в базе — UTC с поясом.

## 3. Ключ повторов (НТ-13)

- Ключ публикации: `площадка:владелец_номер` — `vk:-100123_4567`, `ok:5600101_30418`, `max:<канал>_1842`. Для MAX владелец — имя канала из адреса.
- Разные адреса одного поста (vk.com, vk.ru, m.vk.com, `?w=wall…`, m.ok.ru) разбираются в один ключ и дают одну запись; остальные адреса — в `mergedUrls`.
- Ссылку, которую видит пользователь, сервис строит из ключа (`https://vk.com/wall-100123_4567`); ссылки из текста поста и «чужие» адреса не используются.
- Репост — отдельная запись с пометкой и ссылкой на оригинал (тоже из ключа); пост без текста — запись «текст отсутствует».
- Точные копии текста — хеш нормализованного текста (`content_hash`); перепечатки — кластеры воронки.

**Добавление к контракту (бэклог п. 48), в types.ts ещё не внесено.** `RegionReason.inMySources: boolean` — пост прошёл привязку к краю, потому что источник в списке пользователя (режим «Мои источники»); подпись — «в вашем списке», в XLSX колонка «Почему краевой»: «краевой источник · в вашем списке · упоминается: …». В режиме «Везде» всегда `false`. Тест контракта пока добавляет это поле к схеме сам (`PENDING` в `test_contract_schema.py`).

**Режим по умолчанию (п. 47).** `StartState.defaultMode`: первый запуск — «Везде»; дальше — режим последнего запущенного поиска этого рабочего места; если список источников пуст — «Везде» (НТ-14).

**Поток SSE.** Каждое событие сначала пишется в журнал `search_events` с номером, потом будит читателей. Формат: `id: <номер>`, `event: <тип>`, `data: <SearchEvent JSON>`. Поток закрывается на `finished`, `stopped` или `failed`; каждые 15 с — комментарий `: ping`. Переподключение — заголовок `Last-Event-ID` или `?after=N`: клиент получает пропущенное, поиск при этом не перезапускается (НТ-23). События `connection-lost`/`connection-restored` создаёт клиент. Ошибка запуска (лимиты, нет ключа) — HTTP-ответ с `ApiError`; клиент превращает её в событие `failed`, как требует контракт. Браузерный `EventSource` не умеет передавать заголовок с ключом, поэтому поток читается через `fetch` (ReadableStream); так же — скачивание XLSX.

## 5. Рабочее место по ссылке-ключу (Р8)

- Первый вход: клиент без ключа вызывает `POST /api/workspaces`, получает ключ (32 случайных символа, 192 бита) и хранит его в браузере.
- Ссылка «Открыть на другом компьютере»: `PUBLIC_APP_URL#workspace=<ключ>` — ключ во фрагменте адреса, браузер не отправляет его на сервер при открытии страницы. Веб-версия строит ссылку от своего адреса (`…/app/#workspace=<ключ>`). Клиент сразу убирает ключ из адреса (`replaceState`), ловит ссылку и в уже открытой вкладке (`hashchange`) и не заменяет своё место молча — спрашивает (решение Р-В2).
- В базе — только SHA-256 ключа. Перебор ключей упирается в лимит частоты по IP.
- Изоляция (НТ-7): каждый запрос к поиску, источникам, недавним проверяет принадлежность рабочему месту; чужой поиск неотличим от несуществующего (`404`). Каталог края — общий, только для чтения.

## 6. Лимиты стенда (НТ-6)

| Лимит | Значение | Ответ |
|---|---|---|
| Длина запроса | 20 000 знаков | `422 too-long` |
| Период | до 183 дней (6 месяцев) | `422 invalid` |
| Активных поисков на рабочее место | 1 | `429 too-many-requests`, `retryAfterSec: 10` |
| Поисков на сервере одновременно | `MAX_RUNNING_SEARCHES` (4) | очередь: события `queued {ahead, etaSec}` |
| Запросов с IP в минуту | 240 всего, 12 запусков поиска, 20 созданий/открытий рабочего места, 30 отдельных проверок на ИИ | `429` + `Retry-After` |
| Текст отдельной проверки на ИИ | 20 000 знаков после нормализации | `422 too-long` |
| Тело запроса | 1 МБ JSON, 5 МБ файл импорта, 1 000 строк | `413 too-long` |
| Нейросеть | очередь с ограничением параллельности `LLM_CONCURRENCY` | длина очереди — на странице стенда |
| Квоты площадок | счёт вызовов; при 80% — предупреждение в журнале стенда | `no-access` при исчерпании |

## 7. Безопасность

- **НТ-8 (prompt injection).** Нейросеть получает только пронумерованные предложения и внутренние id `c1…`; текст — данные в JSON, инструкция запрещает выполнять команды из него. Ответ — по JSON-схеме; сервер отбрасывает ответ со ссылками или лишними полями, чужие id, номера несуществующих предложений и двойные ответы. Нет годного ответа → «не проверено ИИ», пост остаётся в подборке. Независимо от воронки сервер ещё раз проверяет номер предложения и отрезки подсветки, выдержку строит сам по границам текста.
- **НТ-9 (XSS).** API отдаёт только JSON (`nosniff`, CSP `default-src 'none'`); текст постов не меняется и не превращается в HTML; ссылки строит сервис из ключа, адреса из текста и `javascript:` не проходят.
- **НТ-10 (XLSX).** Все строки пишутся с типом «текст»; значения, начинающиеся с `= + - @`, табуляции или перевода строки, получают признак «начинается с апострофа». Формул в файле нет (тест читает XML листа). Гиперссылка ставится только на ссылку поста, построенную сервисом.
- **НТ-15 (ключи).** Ключи — только в переменных окружения сервера (`SecretStr`, в логах скрыты); пустое значение в `.env` = «не задано». `.env.example` без значений; тест ищет похожее на ключи в репозитории. Страница стенда не показывает ключей и внутренних адресов.

## 8. Время (НТ-12)

В базе — UTC. Наружу — ISO 8601 с `+07:00` (`Asia/Krasnoyarsk`). Период — календарные дни по Красноярску включительно, «24 часа» — от момента запуска. Пост без даты: `publishedAt: null`, «дата неизвестна», в период не засчитан, виден фильтром; в XLSX дата пустая, пометка в соседней колонке. Дата MAX из номера поста — «≈ время приблизительное». В XLSX даты — настоящие даты Excel по красноярскому времени, подпись пояса — в заголовке колонки и на листе «Сводка».

## 9. Конфигурация и развёртывание

- Все настройки — переменные окружения (`server/.env.example`): база, `PUBLIC_APP_URL`, `CORS_ORIGINS` (сайт и `chrome-extension://<id>`), `DATA_SOURCE` (`fixtures` | `live`), ключи площадок, `OLLAMA_URL`, `LLM_MODEL` (по умолчанию GigaChat 3.1 Lightning `Q6_K`), `LLM_NUM_CTX=8192` (= `OLLAMA_CONTEXT_LENGTH` на gpu-node, чтобы модель не перезагружалась), бюджет нейросети на поиск, `MATCHER`, модель смысла (`EMBEDDING_MODEL`, `EMBEDDING_VERSION`, `EMBEDDINGS_URL`, `EMBEDDINGS_TOKEN`), проверка на ИИ (`AI_DETECT_PROVIDER`, `AI_DETECT_URL`, `AI_DETECT_MODEL`, пороги `AI_CHECK_*`, §13), лимиты.
- `docker compose up -d --build` в `server/`: `db` (pgvector/pgvector:pg16) → `migrate` (`alembic upgrade head`) → `api` (uvicorn, один процесс; модель BERTA скачивается при первом прогреве в том `models`). Порты базы и API открыты только на 127.0.0.1; снаружи — профиль `https` с Caddy (сертификат для `DOMAIN`, SSE без буферизации).
- Один процесс сервера: поиски идут задачами asyncio в нём. Состояние — в базе, поэтому перезапуск не теряет найденное: прерванный поиск закрывается с ошибкой площадки и кнопкой «Повторить» (SC-51). Несколько процессов потребуют общей шины событий (`LISTEN/NOTIFY`) — это следующий шаг, если понадобится.

## 11. Воронка «Э-Отбор» на сервере (`server/matching`, пакет `mm_matching`)

1. **Подключение.** Path-зависимость `mm-matching` и torch для CPU (индекс pytorch-cpu) в `server/pyproject.toml`; `MATCHER=mediamonitor.matcher.funnel:create_matcher` (по умолчанию). Адаптер `matcher/funnel.py` реализует наш `Matcher`, вызовы воронки — через `run_in_threadpool`.
2. **Согласование с сервером.** `publication.sentences` строятся разбиением воронки (`split_sentences`) — номер доказательства указывает на то же предложение; абзацы релиза (`p0`, `p1`…) — тоже от воронки, на них ссылается цитирование (П1). Карточку темы составляет воронка (нейросеть или правила), правки пользователя применяет сервер, в отбор идёт поправленная карточка. Повторы одного поста в источнике (`text_hash`, ТЗ-Ф30) отсекаются, копии в разных источниках склеиваются `group_copies` в группы (Р9). Сервер всё равно проверяет ответ воронки: чужие id, номера предложений и отрезки вне текста не проходят.
3. **Скорость (Р7: база — кэш).** Векторы постов считаются по мере сбора, шагами по 16 постов, и сразу пишутся в `post_embeddings` по ключу «пост × модель с версией × задача»; перед шагом посчитанные раньше векторы берутся из базы. Повторный поиск по тем же постам модель почти не трогает (считаются только запрос и грани карточки).
4. **Провайдер модели смысла** — настройка. Без `EMBEDDINGS_URL` — BERTA на CPU сервера (≈ 0,4 с на статью в 1,5 тыс. знаков на этом компьютере). С `EMBEDDINGS_URL` — сервис gpu-node: `POST /embed {texts, model, prefix, normalize}` → `{model, dim, vectors}`, `GET /health`, `Authorization: Bearer EMBEDDINGS_TOKEN`, пакеты до 256 текстов, таймаут и повтор. Длинный пост клиент режет `chunk_text` (до 1500 знаков, не больше 4 кусков) и усредняет векторы сам, префиксы задач BERTA идут полем `prefix` — векторы совпадают с локальными (косинус 1,000 на коротких и длинных текстах, `scripts/compare_embeddings.py`). Сервис недоступен или отвечает не той моделью — откат на CPU сервера и пометка на странице стенда; через `EMBEDDINGS_RETRY_AFTER_SEC` сервис пробуем снова.
5. **Нейросеть** — по `OLLAMA_URL` (`/api/chat`, `num_ctx` = 8192, `keep_alive` 30 мин — одинаково у воронки и сервера). Бюджет — `LLM_MAX_GRAY` спорных и `LLM_DEADLINE_SEC` на весь поиск, а не на шаг. Без адреса или при отказе — «Спорно», «не проверено ИИ», событие `ai-unavailable`.
6. **Прогрев** (НТ-18) — в фоне при старте: модель смысла (≈ 30 с на CPU), признаки события (Natasha), проверка сервиса gpu-node. Состояние — первыми строками на странице стенда.

**Время поиска на записанных примерах** (CPU этого компьютера, без нейросети, площадки отвечают мгновенно; прогрев модели ≈ 30 с — отдельно):

| Набор | Без кэша | С кэшем в базе | Первые записи в потоке |
|---|---|---|---|
| 51 пост (тема «БДД») | 6,3 с | 4,6 с | 0,5 с |
| 500 постов (нагрузочный набор) | 40,1 с | 5,9 с | 0,4–0,7 с |

Посты примеров короткие (в среднем 100–180 знаков). На настоящих статьях (≈ 1,5 тыс. знаков) BERTA на этом CPU тратит ≈ 0,42 с на текст: 500 таких постов без кэша — около 3,5 минуты отбора, с кэшем — секунды; сервис на видеокарте сокращает и первый раз. Замер — `scripts/bench_search.py`.

## 13. Проверка текста на ИИ (`server/src/mediamonitor/aicheck`)

Решение команды — `04-decisions.md`, «Проверка текста на ИИ» и уточнение. Главное требование — **один и тот же текст даёт один результат** в отдельной проверке (правый клик, экран вставки), в карточках подборки и в «Распространении».

1. **Один метод, одна нормализация.** Все три места идут через `AiCheckService` (`aicheck/service.py`). Нормализация (`aicheck/text.py`) повторяет интерфейс (`web/src/lib/ai-normalize.ts`) шаг в шаг: NFC → удалить U+200B–U+200D, U+FEFF, U+00AD → U+00A0 в пробел → пробельные символы (набор `str.isspace()`, перечислен кодами) в один пробел → обрезать края. Ключ — SHA-256 (hex) нормализованного текста в UTF-8 (одиночный суррогат → U+FFFD, как `TextEncoder`). Слова — части между пробелами. Сверка с интерфейсом — 8 общих тест-векторов (`tests/contract/ai-normalize-vectors.json`, выгружаются `npm run export`) и ключи всех постов имитации.
2. **Текст поста** — `publication.text` (без заголовка). Выделен не весь пост — это другой текст и, возможно, другой результат; в интерфейсе это видно по числу слов.
3. **Уровни.** Меньше `AI_CHECK_MIN_WORDS` (40) слов — `too-short`, модель не вызывается. Иначе по оценке модели: `likely-ai` ≥ `AI_CHECK_LIKELY_THRESHOLD` (0,85), `signs` ≥ `AI_CHECK_SIGNS_THRESHOLD` (0,60), ниже — `unlikely`. Уровень считается из сохранённой оценки по текущим порогам — одинаково везде. Сервис недоступен — `unavailable` (это не «не похоже»).
4. **Кэш `ai_checks`** (миграция `0004`): ключ «хеш текста × модель × версия модели». Новый результат пишется вставкой «если такого ещё нет» и читается обратно — выигрывает первый, в том числе при одновременной записи из двух процессов. Один текст, который проверяют одновременно из двух мест, считается один раз (общее ожидание в процессе). Смена модели или версии — новый ключ, тексты считаются заново. `too-short` и `unavailable` в кэш не пишутся. `checkedAt` у результата модели — время первой проверки.
5. **Провайдеры** (`aicheck/providers.py`, настройка `AI_DETECT_PROVIDER`):
   - `fixture` — без модели: оценка из хеша текста (формула имитации интерфейса, u³ по первым 48 битам), модель `fixture-demo@1`. По умолчанию — только при разработке на записанных примерах (`DATA_SOURCE=fixtures`, `ENVIRONMENT` не `production`); на стенде — только явно: демо-оценку живого текста легко принять за настоящую.
   - `gigacheck` — клиент сервиса на gpu-node, включается заданным `AI_DETECT_URL`.
   - `off` — без детектора: всё, что длиннее 40 слов, — `unavailable`, на стенде предупреждение.
6. **Контракт сервиса детектора** (под него пишется сервис на gpu-node после пробы):
   ```
   POST {AI_DETECT_URL}/ai-detect        Authorization: Bearer {EMBEDDINGS_TOKEN}
   {"texts": ["нормализованный текст", ...]}
   → 200 {"model": "iitolstykh/GigaCheck-Classifier-Multi", "version": "<версия>", "scores": [0.97, ...]}
   ```
   `scores[i]` — вероятность класса «ai» для `texts[i]` (0…1), порядок сохраняется, пакет до `AI_DETECT_BATCH_SIZE` (16). Пустой список — пустой `scores` с `model` и `version` (сервер так проверяет сервис при старте). **Каждый текст оценивается отдельно и одинаково при любом составе пакета**: модель в eval, без случайности, выравнивание пакета не влияет на оценку. Ошибка — код не 200 (401 без токена, 422 неверное тело, 503 модель не посчитала). `model` должна совпадать с `AI_DETECT_MODEL`, иначе — «недоступно» и предупреждение. `version` меняют, когда меняются веса, квантизация или способ подсчёта, — тогда тексты считаются заново.
7. **Подборка — фоном, по мере сбора.** После каждого шага отбора записи уходят в поток сразу; тексты новых записей помечаются «ждут проверки» (у записи нет `aiCheck`) и уходят в очередь проверки поиска. Когда детектор оценил порцию, те же записи приходят ещё раз событием `items` (интерфейс заменяет их по id) с `aiCheck` и новыми `counts.aiLikely` / `aiSigns`. Перед `finished` сервер ждёт очередь не дольше `AI_DETECT_FINISH_WAIT_SEC` (20 с); не успевшее досчитывается после итога и видно в `getSelection`. Остановка поиска очередь не ждёт. Нет ни результата, ни ожидания — `unavailable` (например, детектор был недоступен).
8. **Счётчики и «Распространение».** `SelectionCounts.aiLikely` / `aiSigns` — без исключённых. У размещения «Распространения» `aiCheck` — тот же, что у записи подборки. `SpreadReport.aiRetold = {likelyAi, retold}` — только пересказы без исходного; без подключённого детектора поля нет. В XLSX оценка не идёт.
9. **Добавление по ссылке** проверяет текст сразу после записи (через тот же кэш).
10. **Стенд.** Первой строкой — состояние детектора: демо-оценка, модель с версией и сколько проверено, или предупреждение «сервис детектора недоступен» / «не подключена» (общее состояние — «degraded»). Переходы «недоступна / снова работает» пишутся в журнал стенда. После сбоя `AI_DETECT_RETRY_AFTER_SEC` (60 с) детектор не вызывается, ответы — `unavailable`.
11. **Лимиты:** 30 отдельных проверок в минуту с IP, текст до 20 000 знаков после нормализации (`422 too-long`), не больше `AI_DETECT_CONCURRENCY` (1) одновременных запросов к детектору.

Проверки — `tests/test_ai_check.py`: общие тест-векторы и ключи постов имитации; один текст в разных записях (пробелы, неразрывные, невидимые, `\r\n`, NFD) — один `textHash`, `score`, `level`; отдельная проверка = запись подборки = размещение «Распространения»; повтор и перезапуск — из кэша без модели; смена модели или версии — заново; недоступный сервис — `unavailable` без записи в кэш, предупреждение на стенде, восстановление; `too-short` без модели; фоновая проверка не задерживает выдачу и итог; клиент `gigacheck` по контракту (токен, пакеты, порядок, чужая модель).
